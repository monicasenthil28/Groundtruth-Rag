# Retrieval Regression Testing

`baseline-create` validates a completed benchmark summary and its sibling run files, then writes a versioned aggregate-only baseline. It does not run retrieval. The baseline records the corpus fingerprint, dataset SHA-256 when present, query count, K values, run IDs, aggregate metrics, and latency. It contains no corpus text, query text, hits, or relevance labels. Existing baselines are not replaced without `--force`.

`regress` compares a candidate summary with that baseline under a YAML policy. Corpus fingerprint, dataset hash (when available), and query count must match. Every policy-selected retriever, metric, and required K must exist in both. Unsupported schemas, duplicate JSON keys, malformed values, and nonfinite numbers are rejected as incompatible input rather than scored as regressions. When neither side has a dataset hash, only the dataset filename can be checked; prefer run files with a hash for strong compatibility.

Quality metrics (Recall@K, Precision@K, Hit Rate@K, MRR, nDCG@K) are higher-is-better and use absolute drops. Mean, p50, and p95 latency are lower-is-better and use relative percentage increases. A metric passes below its warning threshold, warns at or above the warning threshold, and fails at or above the failure threshold. Any FAIL makes the overall result FAIL; otherwise any WARN makes it WARN. Disabled metrics are measured in the report but do not influence status. Per-retriever rules can override defaults. Thresholds are engineering policy choices, **not statistical significance tests**.

Latency is sensitive to hardware, warmup, background load, and runtime versions. The example OSHA policy leaves latency gating disabled; enable it only for a controlled environment. A baseline latency of zero with a positive candidate latency cannot support a relative increase calculation and is rejected. A zero-to-zero comparison passes.

Exit codes: PASS is 0, WARN is 0 by default (1 with `--fail-on-warn`), FAIL is 1, and invalid or incompatible input is 2. The CLI writes `regression.json` and `REGRESSION.md` after compatibility succeeds, including WARN and FAIL results. It never edits golden labels.

The baseline and candidate must use the same fixed chunking and human-reviewed dataset. Different corpora, changed relevance judgments, or changed query sets require a new baseline. The aggregate comparison answers whether overall retrieval quality changed. Query diagnostics answer which exact questions changed; they are not new relevance judgments and do not evaluate generation or unanswerable queries.

`query-baseline-create` reads existing run JSON beside a benchmark summary and writes a separate schema-1.0 query baseline. It verifies the aggregate baseline run IDs, corpus fingerprint, dataset hash, query count, and K values. The artifact stores query IDs, relevant chunk IDs, and observed relevant positions only. It never stores query text, source passages, scores, or full hit lists. `regress --query-baseline ...` loads candidate run JSON beside the candidate summary, aligns by query ID, rejects changed query sets or relevance IDs, and computes first relevant rank (null when absent), recall at each configured K, rank movement, new failures, recoveries, and persistent misses. Multiple relevant chunks contribute to recall using the existing retrieval metric function.

Query severity is independent of aggregate policy: new loss at a configured critical K is FAIL, a configured material rank drop is WARN, and recovery or improvement is INFO. `query_regression.enabled: false` keeps query diagnostics in the report without affecting the aggregate gate; this is the initial OSHA policy. Enabling it can apply `fail_on_new_failure_at_k`, `warn_rank_drop`, and optional `max_new_failures_warn` / `max_new_failures_fail` tolerances. Without `--query-baseline`, aggregate-only regression remains backward compatible. An enabled query gate requires the query baseline.

CI exercises the CLI with committed synthetic PASS, WARN, and FAIL candidates. It checks the default WARN exit code (0), strict `--fail-on-warn` exit code (1), and FAIL exit code (1), and uploads machine-readable `regression.json` plus Markdown reports. These fixtures are regression-engine checks, **not** real benchmark evidence. The separate manual OSHA workflow runs retrieval and compares its candidate with baseline v1. Its job summary preserves WARN or FAIL as reported; an optional dispatch input enables strict WARN failure.
